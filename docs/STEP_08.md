# Пункт 8 — временные границы и логика сегментов

## Изменения

- `FrameClock` читает временную метку только после успешного декодирования
  кадра. После неудачного `read()` в конце видео метаданные времени не читаются.
  Повторяющаяся, отрицательная, убывающая или нечисловая метка заменяется
  следующим номинальным шагом по FPS. Некорректный FPS заменяется на 25.
- Конец декодированной последовательности — время последнего успешно
  прочитанного кадра плюс один номинальный кадр. Он сохраняется и при пропуске
  кадров для анализа; потеря активного сегмента на EOF устранена.
- `MotionSegments` отделяет последнюю положительную оценку движения от начала
  подтверждающей паузы. Подтверждение паузы закрывает сегмент по последнему
  движению, а не по времени обнаружения достаточной тишины.
- Минимальная длительность проверяется без завершающей паузы. Короткие
  внутренние паузы, после которых движение возобновилось до подтверждения
  остановки, остаются внутри одного события. Это длительность события,
  а не сумма только положительных измерений.
- При EOF положительное последнее измерение удерживается до конца
  декодированной последовательности, включая пропущенный для анализа хвост.
  Если последнее измерение отрицательное, тихий хвост не добавляется, даже
  когда его длины не хватило для подтверждения паузы.
- Порядок зафиксирован: закрытие события → фильтр минимальной длительности →
  ограничение интервалов декодированной последовательностью → объединение.
  Несколько отброшенных коротких всплесков не превращаются объединением
  в подходящее длинное событие.
- `merge_close_segments` сортирует копию входных интервалов, проверяет
  конечность/неотрицательность/порядок границ, объединяет вложенные интервалы
  через максимум концов. Пересечения и соприкасающиеся интервалы объединяются
  даже при merge_gap=0. Неверные интервалы отклоняются явно.

## Проверки

75 тестов прошли, из них 15 новых сценариев временных границ.

Проверены: вложенные/неотсортированные интервалы; нулевой и точный промежуток;
ошибочные границы; короткое движение с длинной завершающей паузой; подтверждение
паузы без удлинения сегмента; тихий хвост на EOF; короткая внутренняя пауза;
фильтрация перед объединением; точный порог длительности и пропущенный хвост;
повторяющиеся/нечисловые метки; реальные видео с пропуском кадров; отсутствие
запроса времени после EOF; пустой и однокадровый вход; реальные паузы разной
длины; реальные синтетические видео с FPS 10 и 30 (основные fixtures — 25).

Результат `tools/check_baseline.py` при стандартных параметрах:

| Видео | До пункта 8 | После |
|---|---|---|
| static.mp4 | Нет сегментов | Нет сегментов |
| motion_middle.mp4 | 1–3.68 с | 1–3.20 с |
| motion_to_end.mp4 | Нет сегментов (ошибка) | 2–6.00 с |
| motion_with_audio.mp4 | 1–4.68 с | 1–4.20 с |

Автопороги не изменились. Декодирование и экспорт тестовых результатов прошли.
На реальном motion_middle увеличение min_pause с 0.5 до 2 секунд даёт одинаковый
интервал; min_motion=3 отклоняет событие независимо от длинной завершающей паузы.

## Ограничения

Границы определяются положительным сглаженным показателем, а не истинной
физической активностью объекта. Сглаживание из пяти измерений пока сохранено:
например, исчезновение объекта в 3.0 с даёт положительные оценки до 3.2 с.
Сглаживание по времени и запас до/после движения — пункт 9.

Корректные возрастающие метки OpenCV используются как есть. Для конца последнего
кадра и отсутствующих меток используется номинальный FPS; точность тайминга
произвольного VFR не гарантируется. Частота анализа ограничивает точность при
пропуске кадров. Преждевременный отказ декодирования пока трактуется как конец
доступной последовательности, а не достоверный физический конец файла.

Экспорт по-прежнему использует stream copy с ограничениями ключевых кадров.
Точный экспорт — пункт 11. Эти изменения исправляют интервалы анализа, а не
обещают покадровую точность уже закодированного выходного файла.
